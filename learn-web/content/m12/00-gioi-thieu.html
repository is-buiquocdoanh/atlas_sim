Từ "cấu hình" sang "tự viết code điều khiển"

Module 10 — gửi 1 goal, đợi Nav2 tự lo hết. Module 11 — Nav2 tự khắc phục sự cố khi kẹt. Cả hai module đó bạn chỉ cấu hình (YAML, XML), chưa viết dòng Python nào điều khiển Nav2. Module này đổi hướng: tự viết code gửi nhiều điểm liên tiếp, đọc tiến độ khi đang chạy, và hủy giữa chừng theo logic riêng.

Sau module này bạn sẽ

  • Giải thích được vì sao NavigateToPose/FollowWaypoints PHẢI là action, không thể là service — bằng đúng 3 đặc điểm: lâu, có feedback, hủy được
  • Dùng được 4 hàm cốt lõi của BasicNavigator: waitUntilNav2Active(), followWaypoints(), isTaskComplete()/getFeedback(), cancelTask()
  • Đọc hiểu waypoint_demo.py thật, kể cả gotcha rcl_shutdown already called khi Ctrl+C — không phải lý thuyết, là lỗi thật gặp lúc soạn bài
  • Tự viết patrol_node.py trong atlas_apps — package SV tự viết, tách khỏi code mẫu — tuần tra vô hạn, phân biệt đúng CANCELED (người dùng hủy) với FAILED (lỗi thật)

Vì sao module này đứng SAU Recovery/BT (Module 11), không phải ngay sau Module 10

Gửi 1 goal rồi đợi (Module 10) chỉ cần Nav2 chạy đúng. Gửi NHIỀU goal liên tiếp, đọc feedback khi đang chạy, và tự quyết định hủy khi nào — cần hiểu trước bt_navigator đã tự xử lý thất bại/retry ra sao (Module 11), để không nhầm lẫn 2 tầng khác nhau: Nav2 tự recovery bên trong 1 goal, và code của BẠN tự quyết định làm gì SAU KHI 1 goal xong (tiếp tục, lặp lại, hay dừng).

Chuẩn bị

cd ~/atlas_sim
colcon build --packages-select atlas_slam atlas_apps
source install/setup.bash

atlas_apps là package TRỐNG, cố tình — nơi bạn tự viết bài tập của module này (cấu trúc package, Module 1), khác atlas_slam/scripts/ chứa code mẫu đã viết sẵn để tham khảo.

Bản đồ module

ActionMô hình giao tiếp thứ 3 — lâu, có feedback, hủy được (khác topic/service)
BasicNavigatorWrapper Python quanh action Nav2 — không phải tự viết ActionClient thủ công
waypoint_demo.pyMẫu tham khảo: 4 điểm, 1 vòng, có xử lý Ctrl+C sạch
patrol_node.pyBài tập: tuần tra vô hạn, tự viết trong atlas_apps
